# WA-1 workflow contract review (ZA-1A–D input)

Status: source/design review, 2026-10-03. WA-1 decisions are selected and the neutral package is implemented and locally qualified under WA-2; see the resolution below and release handoff. No runtime dispatch hook, adapter or persistence change has been implemented. Sequence WA-1, WA-2/3 publication, Zhinu ZA-2/3/4/6, then Hufu HA-1/2/3. Keep that order.

## Review result

The initial sketch raised open design questions about host identity provenance, bounded requirements, per-attempt freshness, policy-versioned requirement semantics and closed outcomes. This follow-up reviews the selected contract in [workflow-authorization-contract.md](workflow-authorization-contract.md), which resolves those design questions subject to the conformance notes at the end. The product-neutral seam remains additive and does not move workflow execution machinery into the shared package.

### Original sketch recommendations (resolved by the selected contract)

- **Who and what is being authorized.** Model authenticated invocation, tenant/subject, workflow execution, optional parent, operation ID/path, actual invocation/attempt identity, and declared requirements as distinct, bounded values. A host-authenticated identity is evidence supplied by the trusted host boundary; strings in a context record do not authenticate themselves. The adapter must never resolve identity from ambient user state, arbitrary workflow metadata, a requirement label, or old receipt.
- **Fresh attempt and fence.** Give each actual callback dispatch a stable, opaque invocation-attempt identity. Carry runtime-owned freshness/fence facts in a runtime-neutral form that can be compared by the runtime after the asynchronous authorizer call. Do not expose a Zhinu lease-generation type or require all engines to use counters. A matching allow is usable only for the exact current attempt/context; the runtime must revalidate its own current ownership/revision immediately before dispatch. A stale allow is evidence of a past check, not a dispatch token.
- **Requirements and exact identity.** Version the requirement schema and every adapter mapping. Require bounded count and encoded size, validated identifiers and canonical ordering/encoding. Freeze/copy nested values at construction; `IReadOnlyCollection<T>` alone does not prevent mutation by its owner. Define canonical plan ID/revision/fingerprint and a deterministic requirements/plan digest (including domain/schema IDs), with explicit case and path semantics. Store that digest with evidence and bind approval/resume to it. Unknown schemas or unmapped requirements fail closed. An empty list has explicit configured behavior and is never an implicit Hufu permit.
- **Closed outcomes.** Represent exactly `Allowed`, `Denied`, `ApprovalRequired`, and `Unavailable` as the supported categories. Reject null/malformed/unknown values. Denial reasons never imply approval. Provider throws/timeouts map to unavailable; caller cancellation remains cancellation. Unavailable is not an activity attempt: any retry or parking is runtime-owned and bounded/configurable so an outage cannot consume activity retry budget or loop indefinitely. Every non-Allowed result, missing evidence, or stale fence invokes zero protected callbacks.
- **Evidence and approval.** Persist bounded provider identity, outcome, timestamp/correlation, exact context/attempt and plan/requirements digest before dispatch or durable suspension. Evidence write failure blocks dispatch. `ApprovalRequired` is produced only by trusted approval orchestration, then parked durably without holding a worker lease. Duplicate/lost/stale wakes are idempotent; after restart or approval, the runtime reconstructs the exact current context and calls the authorizer again. Never persist secrets or treat a prior allow as current authority.
- **Boundary of guarantee.** Workflow authorization gates named workflow callbacks only. It is neither a native-code sandbox nor a permit for IO/model effects. Preserve Hufu.IO/Luban admission, discovered-resource checks, current per-resource authority and concrete mutation-start guarantees. The asynchronous callback seam cannot claim the legacy shared-SQLite atomic revocation/start behavior.

## Hufu mapping and compatibility disposition

`Penghou.Hufu/src/Penghou.Hufu/AuthorityModel.cs:8–19, 137–169` defines current `AuthorityStatus` (`Unavailable`, `Deny`, `Permit`), `AuthenticatedAuthorityContext` (tenant, subject, run, revision, fence), and an action/workspace/path/request-identity request. `AuthorityRequestAuthorizer.cs:4–67` requires a valid recorded decision for `IsAuthorized`; malformed inputs deny, missing/mismatched current snapshots or evidence return unavailable, and caller cancellation propagates. The future `Penghou.Hufu.Workflow` adapter can map a versioned `ExecutionRequirement` to exact Hufu action/scope requests and bind Hufu request identity to the canonical execution-attempt/requirement digest. It must receive tenant/subject from trusted host authentication and translate Hufu unavailable/deny/permit without collapsing them. Hufu does not currently return a workflow approval outcome; trusted approval orchestration must be a separate explicit source. `AuthorityOperationStart` is a distinct legacy atomic gate, not the workflow preflight adapter.

Keep existing Zhinu public APIs where they are. `WorkflowContext` performs durable orchestration; `WorkflowStepContext` carries run/step/attempt operations; `IWorkflowStepResolver` and leases control Zhinu activation; `StepOptions`, retry, child, loop, compensation and declarative definition types carry runtime/durable semantics. Their dependencies and persisted identities make wholesale extraction inappropriate for this seam. No existing type needs to move to create the new capability contract, so type forwarders are unnecessary for the initial additive design. If later code actually relocates a public type, use forwarders and old-binary/source/serializer probes or record a deliberate preview break.

Zhinu's `docs/public-api-policy.md` says preview.15 is frozen with additive changes allowed; renames/removals/default or durable-state semantic changes require a new preview minor and release notes. The neutral contract package is new and can be versioned independently. Requirements added to existing durable definitions/options still need API-baseline and serialization/version decisions before implementation. Do not describe this review as implementation or publication.

## Initial sketch review (superseded)

The identity, bounds, trust, error, approval and runtime-transition concerns recorded earlier in this review were blockers against the original sketch. The later selected contract resolves those design questions; retain the source dispatch map above as implementation acceptance input. One naming change from the interim candidate is explicit: the selected closed human-approval outcome is `ApprovalRequired`, alongside `Error`, rather than the interim `Pending` label.
## Review against the selected contract

The initial sketch blockers are resolved by the normative [workflow authorization contract](workflow-authorization-contract.md), which now supersedes the earlier open-question list above. The selection defines the neutral `ExecutionIdentity`/context/requirement/result types, opaque execution freshness, paired plan identity, one-use request IDs bound to the exact retained snapshot, external host authentication and scope lookup, optional opaque scope references with schema-required semantics, immutable/count/byte-bounded values, and the closed `Unavailable`/`Allowed`/`Denied`/`ApprovalRequired`/`Error` outcomes. It assigns callback activation, evidence, fence recheck, pending/restart/retry, default-provider downgrade protection and loop callback declarations to the runtime. The earlier advice that WA itself should standardize a digest algorithm is narrowed: WA defines the exact fields and binding obligations; a runtime/approved-plan owner can own the versioned codec/hash.

The selected contract also makes the initial compatibility review conclusive: this is an additive package; no existing Zhinu public type is moved or redefined, so forwarders are not applicable to the first seam. Existing engine/service/durable values remain Zhinu-owned. Hufu mapping remains typed and versioned, with host-authenticated identity/scope binding outside WA and no translation of denial into approval. The package's source and normative design do not establish that a Zhinu runtime or Hufu adapter has implemented these guarantees.

**Design review disposition:** WA-1 contract design and ZA-1 design input are closed against the selected normative document, with the small conformance/clarity notes below tracked for WA-2; this is not evidence of WA-2 qualification, publication, exhaustive runtime call-graph proof, ZA implementation, or HA integration.

- Count conformance is resolved: the constructor now rechecks the reported count after enumeration, and a changing-count regression fixture rejects that input.
- Ordering is resolved in the normative profile: enumeration order defines the frozen sequence; runtimes supply deterministic retained arrays/lists and hash the actual snapshot, never incidental HashSet traversal.
- Wire handling is resolved as an explicit host obligation: bound raw bytes and reject unrecognized properties under strict profiles. The serializer conformance test exercises UnmappedMemberHandling.Disallow; the package remains a typed-value boundary rather than a transport parser.
- Non-resource targets are clarified: Resource is a retained logical operation/execution target under its vocabulary, while ScopeReference can be absent. No fabricated filesystem path, ambient target or universal wildcard is introduced.

The source mapping and path-specific dispatch obligations earlier in this review stay open as implementation acceptance gates: actual post-claim/pre-activation placement, declarative resolution movement, compensation gating, loop body/predicate declarations, direct/hosted/child/restart coverage, post-await fence checks, evidence ordering, pending approval state/reconciliation, and activity-versus-authorization retry accounting all require runtime implementation and integration evidence. Preserve the frozen legacy atomic-start profile until ZA-5B justifies replacement or consumer retirement.
